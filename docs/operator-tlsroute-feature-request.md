# Feature request draft: TLS-passthrough (TLSRoute / `routing.tcp`) support in NebariApp

> Draft for a nebari-dev/nebari-operator issue. Not filed — kept in the
> dask-gateway-pack repo so a maintainer can file/adapt it.

## Summary

`NebariApp` today reconciles HTTP only: one hostname, one backend Service,
`HTTPRoute`s on the shared Envoy Gateway, per-app HTTPS **Terminate**
listeners (`api/v1/nebariapp_types.go`, `reconcilers/{routing,tls}/`).
Some workloads carry L4 traffic that is TLS end-to-end and routed by SNI —
the gateway must forward the raw TLS stream without terminating it. The
Gateway API models this as a `TLSRoute` attached to a listener with
`tls.mode: Passthrough`; Envoy Gateway supports both. The operator cannot
express either, so packs with such traffic can only keep it in-cluster.

## Concrete motivating case: dask-gateway-pack

dask-gateway's client↔scheduler protocol (dask-gateway 2026.3.0):

- Every Dask cluster gets its own TLS credentials, generated by the gateway
  and **terminated at the scheduler pod** (mutual TLS).
- The `dask_gateway` client always connects through a proxy endpoint,
  dialing `gateway://<proxy-address>/<cluster>` and sending TLS SNI
  `daskgateway-<namespace>.<cluster-name>` (`dask_gateway/comm.py`); the
  proxy routes purely on SNI, passthrough. There is no direct-to-scheduler
  mode and no plain-HTTP fallback.
- Upstream ships a bundled Traefik for this (per-cluster `IngressRouteTCP`
  with `tls.passthrough: true`). In the Nebari pack, that Traefik is kept
  strictly in-cluster (ClusterIP), so **off-cluster dask clients cannot
  connect to schedulers at all** — they can reach the REST api through the
  NebariApp route, create clusters, and then fail to connect. This is the
  v0.1 limitation we want to remove.

Note the SNI shape: the varying part (`<cluster-name>`, a UUID) is the
*second* DNS label, so no single listener `hostname` wildcard can cover it
(wildcards are leftmost-label only). A passthrough listener therefore needs
either no hostname (match-all on a **dedicated port**) or per-route exact
hostnames — which is exactly how Gateway API TLSRoute works.

## Proposed spec surface (sketch)

```yaml
apiVersion: reconcilers.nebari.dev/v1
kind: NebariApp
spec:
  hostname: dask-gateway.example.com
  service: { name: api-dask-gateway-pack, port: 8000 }
  routing:
    routes: [...]
    # NEW: L4 passthrough routing
    tcp:
      - name: scheduler
        # Listener the operator creates/owns on the shared Gateway:
        listener:
          port: 8786            # dedicated port; protocol TLS, mode Passthrough
        # Either a static SNI list, or a selector for routes managed by the
        # app itself (see "Alternative" below):
        sniHostnames:
          - "daskgateway-*"     # illustrative; exact semantics TBD
        service:
          name: some-backend    # optional when routes are app-managed
          port: 8786
```

Operator responsibilities, mirroring the existing HTTP/TLS reconcilers:

1. Upsert a named `TLS`/`Passthrough` listener on the shared Gateway
   (same upsert-one-named-listener pattern the TLS reconciler already uses
   for per-app HTTPS listeners), with `allowedRoutes` scoped to the app's
   namespace.
2. Create `TLSRoute`s (`gateway.networking.k8s.io/v1alpha2`) for static
   backends, or — for the dask case, where routes are inherently dynamic
   (one per running cluster) — just own the listener and let the app's own
   controller attach namespace-local TLSRoutes to it.
3. Surface readiness in a new condition (e.g. `TCPRoutingReady`) and the
   listener/port in `status`.

### Alternative considered

The pack patching the shared Gateway itself (as nebari-llm-serving-pack's
operator does for its shared listeners) was prototyped and rejected for
dask-gateway-pack: shared-Gateway mutation belongs to exactly one owner,
and that should be the operator.

## Dependencies / notes

- Envoy Gateway supports TLSRoute passthrough today; the Gateway's
  LoadBalancer must expose the extra port (Envoy Gateway adds the Service
  port automatically when the listener exists).
- `TCPRoute` (no SNI, one backend per listener/port) is a simpler sibling
  that would fall out of the same work; dask-gateway specifically needs
  SNI, i.e. TLSRoute.
- Secondary benefit for dask-gateway-pack: the same mechanism plus
  dynamic per-cluster HTTPRoutes would enable externally shareable
  dashboard URLs; TLSRoute is the part only the operator can provide.
